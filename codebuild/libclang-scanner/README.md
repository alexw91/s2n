# Libclang Scanner

## Overview

This is a custom static analysis framework for C projects. It parses source files using libclang's Python bindings and runs pluggable checks against the AST.

It exists because off-the-shelf tools (cppcheck, clang-tidy, semgrep) cannot enforce certain rules with zero false positives. For example: "every local variable must be initialized" sounds simple, but tools that rely on token-level pattern matching break on macro-expanded declarations like `DEFER_CLEANUP(struct s2n_blob blob, s2n_blob_free)`. Libclang parses the post-preprocessor AST, so macro expansion is transparent — no special-casing required.

The scanner targets the gap between compiler warnings (which catch some things) and manual review (which doesn't scale). Every check must produce zero false positives. If a check produces a false positive, the check is wrong and must be fixed — not suppressed.

## Usage

From the repository root:

```bash
# Install libclang bindings
pip install libclang

# Generate compile_commands.json (required for parsing)
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# Run the scanner
./codebuild/libclang-scanner/s2n-scan.sh
```

`s2n-scan.sh` is a thin wrapper that invokes `harness.py` with the s2n source directories pre-configured. It will generate `compile_commands.json` automatically if missing.

## CLI Interface

```bash
python3 harness.py --compile-commands <path> --source-dirs <dir1> [dir2 ...]
```

**Arguments:**

- `--compile-commands` — Path to `compile_commands.json` (generated by cmake with `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`). The harness extracts per-file include paths and defines from this database.
- `--source-dirs` — One or more directories (relative to repo root) that define the scan scope. Only findings in these directories are reported. Headers outside these directories are parsed but not flagged.

**Exit codes:**

| Code | Meaning |
|------|---------|
| 0 | No findings. All checks pass. |
| 1 | Findings detected. CI should fail. |
| 2 | Configuration error, self-test failure, or unexpected condition. CI should fail loudly. |

**Check discovery:** Every `.py` file in `checks/` (excluding `_`-prefixed files) is imported automatically. If it exports a callable `check()` function, it runs. No registration step, no configuration file. Drop a file in the directory and it activates.

## Architecture

```
codebuild/libclang-scanner/
├── harness.py              # CLI entry point, orchestration
├── utils.py                # Platform detection, arg extraction, path utilities
├── s2n-scan.sh             # s2n-specific wrapper (sets source-dirs)
├── checks/
│   ├── no_uninit_locals.py # Check: every local must be initialized
│   └── exhaustive_switch.py# Check: non-enum switches need default:
└── tests/
    ├── test_no_uninit_locals.c            # Synthetic test file
    └── test_no_uninit_locals.expected.json # Golden file
```

**Data flow:**

1. Load `compile_commands.json` — one entry per `.c` file with its compiler flags.
2. Filter entries to files under `--source-dirs`.
3. Run self-tests (parse synthetic `.c` files, compare against golden `.expected.json`).
4. For each translation unit: parse with libclang → get AST root cursor → run every check function against it.
5. Deduplicate findings (same header parsed via multiple `.c` files produces duplicates).
6. Output findings sorted by file and line. Exit 1 if any, 0 if none.

**Separation of concerns:** The harness handles orchestration (argument parsing, file discovery, deduplication, output formatting). Checks are pure functions that receive a cursor and append to a list. Checks have no knowledge of the CLI, compile database, or output format.

## How to Add a New Check

1. Create `checks/my_new_check.py`.
2. Define a module-level `CHECK_ID` string (used in output and golden files):

```python
CHECK_ID = "my-new-check"
```

3. Implement the check function with this exact signature:

```python
def check(cursor, source_file, source_dirs, findings):
    """
    Args:
        cursor: clang.cindex.Cursor — root cursor of the translation unit
        source_file: str — absolute path to the .c file being parsed
        source_dirs: list[str] — absolute paths of directories in scope
        findings: list[dict] — append finding dicts here
    """
```

4. Walk the AST recursively. When you find a violation, append a dict:

```python
findings.append({
    "file": filepath,           # str: absolute path
    "line": loc.line,           # int: 1-based line number
    "column": loc.column,       # int: 1-based column number
    "variable": cursor.spelling,# str: name of the relevant symbol (or "switch", etc.)
    "type": type_spelling,      # str: type description for the message
    "function": func_name,      # str: enclosing function name
    "check_id": CHECK_ID,       # str: your check's identifier
    "message": "Human-readable explanation of the violation.",
})
```

5. Add a self-test: create `tests/test_my_new_check.c` and `tests/test_my_new_check.expected.json`.

6. Run `s2n-scan.sh` to verify.

## Libclang API Reference for Check Authors

### Key CursorKind Values

| CursorKind | What it represents |
|---|---|
| `VAR_DECL` | Local variable or file-scope variable declaration |
| `PARM_DECL` | Function parameter declaration |
| `FUNCTION_DECL` | Function definition or declaration |
| `SWITCH_STMT` | A `switch(expr) { ... }` statement |
| `CASE_STMT` | A `case VALUE:` label inside a switch |
| `DEFAULT_STMT` | A `default:` label inside a switch |
| `COMPOUND_STMT` | A `{ ... }` block |
| `IF_STMT` | An if statement |
| `FOR_STMT` | A for loop |
| `UNEXPOSED_EXPR` | Implicit cast or conversion inserted by the compiler |
| `DECL_REF_EXPR` | A reference to a declared name (variable, function, enum constant) |
| `MEMBER_REF_EXPR` | A `.field` or `->field` access |
| `PAREN_EXPR` | Parenthesized expression |
| `ENUM_DECL` | An `enum { ... }` declaration |
| `INIT_LIST_EXPR` | A `{ 0 }` or `{ .field = val }` initializer |

### Getting Type Information

```python
cursor.type                    # The Type object for this cursor
cursor.type.spelling           # Human-readable type name: "uint8_t", "struct s2n_blob"
cursor.type.kind.name          # Type kind string: "UINT", "RECORD", "ENUM", "ELABORATED", "POINTER"
cursor.type.get_canonical()    # Resolves typedefs: uint8_t → unsigned char
cursor.type.get_declaration()  # For ELABORATED/TYPEDEF types, returns the underlying ENUM_DECL or STRUCT_DECL
```

### Walking Children

```python
for child in cursor.get_children():
    # child is another Cursor
    if child.kind == CursorKind.VAR_DECL:
        ...
```

Use `cursor.kind.is_expression()` to test if a cursor is any expression kind.

### Getting Location

```python
loc = cursor.location
loc.file        # File object (None for builtin locations)
loc.file.name   # Absolute path string
loc.line        # 1-based line number
loc.column      # 1-based column number
```

### semantic_parent

`cursor.semantic_parent` returns the semantic parent of a **declaration**. For a local `VAR_DECL`, this is the enclosing `FUNCTION_DECL`. For a top-level function, it's the translation unit.

`semantic_parent` is only meaningful for declarations. For statements (`SWITCH_STMT`, `IF_STMT`, `FOR_STMT`), it returns `None` or the translation unit — not the enclosing function. See the pitfalls section below.

## Known Libclang Pitfalls and Workarounds

### Token Inspection Fails for Macro-Expanded Declarations

`cursor.get_tokens()` returns the pre-expansion source text. For a declaration like:

```c
DEFER_CLEANUP(struct s2n_blob blob, s2n_blob_free);
```

The tokens are `DEFER_CLEANUP`, `(`, `struct`, etc. — the macro invocation, not the expansion. You cannot determine whether the variable has an initializer by looking at tokens.

**Workaround:** Use child-cursor inspection. A `VAR_DECL` with an initializer has an expression child (e.g., `INIT_LIST_EXPR`, `INTEGER_LITERAL`, `CALL_EXPR`). A `VAR_DECL` without an initializer has no expression children. This works uniformly for direct and macro-expanded declarations because the AST is post-preprocessor.

### semantic_parent is None for Statements

`cursor.semantic_parent` only works for declarations (`VAR_DECL`, `FUNCTION_DECL`, `ENUM_DECL`, etc.). For statements like `SWITCH_STMT` or `IF_STMT`, it returns `None` or the translation unit — never the enclosing function.

**Workaround:** Track the enclosing function name during the recursive walk:

```python
def _walk(cursor, findings, enclosing_function):
    if cursor.kind == CursorKind.FUNCTION_DECL:
        enclosing_function = cursor.spelling
    if cursor.kind == CursorKind.SWITCH_STMT:
        _check_switch(cursor, findings, enclosing_function)
    for child in cursor.get_children():
        _walk(child, findings, enclosing_function)
```

### Enum Integer Promotion in Switch Conditions

In C, enum values are promoted to `int` or `unsigned int` in expressions. When you inspect the type of a switch condition:

```c
enum my_state state = INITIAL;
switch (state) { ... }
```

The top-level `UNEXPOSED_EXPR` (the condition) reports `type.kind.name == "UINT"` because the compiler inserted an implicit promotion. The actual enum type is one level deeper — the child `UNEXPOSED_EXPR` or `DECL_REF_EXPR` before the promotion.

**Workaround:** Walk down through `UNEXPOSED_EXPR`, `PAREN_EXPR`, and `DECL_REF_EXPR` children, checking `cursor.type.kind.name` at each level. If any node in the chain has type kind `ENUM` or `ELABORATED` (resolving to an enum via `get_canonical()` or `get_declaration()`), the condition is enum-typed.

### macOS `core.ignoreCase=true` and Gitignore

On macOS, git uses case-insensitive matching by default. A `.gitignore` pattern like `Python-*` (intended to exclude CPython source tarballs) will also match `python-libclang-scanner` because `P` matches `p`.

**Workaround:** We named this directory `libclang-scanner` (not `python-libclang-scanner`) to avoid collisions with common gitignore patterns.

### Function Parameters Are PARM_DECL, Not VAR_DECL

Function parameters use `CursorKind.PARM_DECL`, a distinct kind from `CursorKind.VAR_DECL`. This means the uninit-locals check (which only examines `VAR_DECL` nodes) naturally excludes parameters without any special-case logic.

## Check: no-uninit-locals

**Rule:** Every local variable must have an initializer at its declaration site.

**Rationale:** Uninitialized memory is the root cause of entire vulnerability classes. Zero-initialization at declaration eliminates use-before-init bugs, stack information leaks, and makes code behavior deterministic regardless of compiler/platform.

**Detection method:**

1. Find `VAR_DECL` nodes in the AST.
2. Confirm `cursor.semantic_parent.kind == CursorKind.FUNCTION_DECL` (it's a local, not a global or file-scope static).
3. Confirm `cursor.location.file.name` is under one of the `source_dirs`.
4. Check for expression children via `cursor.get_children()`. If no child `is_expression()`, the variable has no initializer → finding.

**What it catches:**
- Direct declarations: `int x;`, `char *ptr;`, `struct s2n_blob blob;`
- Macro-expanded declarations: `DEFER_CLEANUP(struct s2n_blob blob, s2n_blob_free);`
- Nested blocks: variables inside `if`, `for`, `while` bodies
- All types: scalars, pointers, structs, arrays

**What it ignores:**
- Function parameters (`PARM_DECL`, not `VAR_DECL`)
- Global/file-scope variables (semantic parent is not a function)
- Variables in headers outside `source_dirs`
- Variables with initializers (have expression children)

**Fix patterns:**

```c
struct s2n_blob blob = { 0 };       // Structs and arrays
int count = 0;                       // Scalars
uint8_t *ptr = NULL;                 // Pointers
DEFER_CLEANUP(struct s2n_blob b = { 0 }, s2n_blob_free);  // Macro-expanded
```

## Check: exhaustive-switch

**Rule:** Every `switch` on a non-enum type must have a `default:` case.

**Rationale:** A `switch` on `int`, `uint8_t`, or other non-enum types without a `default:` silently ignores unexpected values. The silent TLS 1.3 record drop vulnerability (penpal-12) had exactly this root cause: a `uint8_t` wire value fell through a switch with no default handler.

**Why enum switches are excluded:** Clang's `-Wswitch -Werror` already enforces compile-time exhaustiveness for enum-typed switches — a missing enum value is a build failure. Adding a `default:` to an enum switch would actually *disable* that compiler check, because the default would catch the missing value at runtime instead of at compile time.

**Detection method:**

1. Find `SWITCH_STMT` nodes in the AST.
2. Search the switch body subtree for a `DEFAULT_STMT`. If found, pass.
3. Determine if the switch condition is enum-typed by walking the condition's type chain:
   - Get the first child of the `SWITCH_STMT` (the condition expression).
   - Recursively check `cursor.type.kind.name` for `"ENUM"` or `"ELABORATED"`.
   - For `ELABORATED`: call `cursor.type.get_canonical()` and `cursor.type.get_declaration()` to resolve through typedefs.
   - Walk into `UNEXPOSED_EXPR`, `PAREN_EXPR`, `DECL_REF_EXPR`, and `MEMBER_REF_EXPR` children to find the pre-promotion type.
4. If the condition is enum-typed, skip (compiler handles it). If non-enum and no default → finding.

**The type chain walk explained:**

```c
switch (record_type) { ... }
//      ^^^^^^^^^^^^ type chain for uint8_t variable:
//
//  SWITCH_STMT
//   └─ UNEXPOSED_EXPR  type.kind.name="UINT"  (implicit int promotion)
//       └─ DECL_REF_EXPR  type.kind.name="UCHAR"  (the actual variable type)
//
// Neither is ENUM → non-enum switch → needs default.
```

```c
switch (state) { ... }
//      ^^^^^ type chain for enum variable:
//
//  SWITCH_STMT
//   └─ UNEXPOSED_EXPR  type.kind.name="UINT"  (enum promoted to unsigned int)
//       └─ UNEXPOSED_EXPR  type.kind.name="ENUM"  (pre-promotion enum type)
//
// ENUM found in chain → enum switch → skip (compiler enforces).
```

## Self-Tests

The `tests/` directory contains golden-file self-tests that run before the real scan.

**Mechanism:**

1. For each `*.expected.json` file, find the matching `.c` file.
2. Parse the `.c` file using libclang with platform args (no compile_commands needed — test files are self-contained).
3. Run all check plugins against the parsed AST.
4. Compare actual findings (line, column, variable, check_id) against the golden file.
5. If they diverge: print the diff, exit 2.

**Purpose:** Detect libclang version incompatibility before scanning real code. Different libclang versions may represent the AST differently (e.g., column numbers shift, implicit nodes appear or disappear). The self-test catches this immediately with a clear error message rather than producing silent false positives or false negatives on real code.

**If a self-test diverges:** Either the golden file needs updating (libclang version changed but behavior is correct) or a check has a bug. Investigate before updating the golden file — the divergence may indicate a real problem.

**Golden file format (`test_no_uninit_locals.expected.json`):**

```json
[
  {"line": 26, "column": 22, "variable": "blob", "check_id": "no-uninit-locals"},
  {"line": 31, "column": 9, "variable": "x", "check_id": "no-uninit-locals"}
]
```

Only `line`, `column`, `variable`, and `check_id` are compared. Other fields (message, type, function) are informational and allowed to change without failing the self-test.

## Design Principles

1. **Zero false positives.** No suppressions, no allowlists. If the check produces a false positive, the check is wrong. Fix the check or narrow its scope.

2. **Zero name-based heuristics.** The scanner never matches on function names, variable names, or macro names. All decisions are structural (AST node kinds, parent relationships, type information).

3. **Fail loud on unexpected conditions.** Exit 2 on configuration errors, missing directories, self-test failures, and parse errors. The scanner should never silently produce incomplete results.

4. **Generic enough for any C codebase.** Nothing in the framework is s2n-specific. The checks, source directories, and compile_commands path are all parameters. The same framework can scan AWS-LC or any other C project with a `compile_commands.json`.

5. **Two-PR rollout.** When introducing a new check: first PR fixes all existing violations. Second PR enables the scanner check. This ensures the check starts with zero findings and CI never sees a wall of pre-existing violations.

## CI Integration

The scanner runs in `.github/workflows/ci_linting.yml` as the `hardening-scan` job:

```yaml
hardening-scan:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v7
    - name: Install dependencies
      run: |
        sudo apt-get update
        sudo apt-get install -y cmake clang
        pip install libclang
    - name: Generate compile_commands.json
      run: cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
    - name: Run hardening scanner
      run: ./codebuild/libclang-scanner/s2n-scan.sh
```

**Dependencies:** `cmake`, `clang` (for system headers), `pip install libclang`.

**Estimated runtime:** ~30–45 seconds for the full s2n codebase (~400 translation units). The bottleneck is libclang parsing, not the check logic.

**Failure modes:**
- Exit 1 (findings detected) → job fails, PR cannot merge until violations are fixed.
- Exit 2 (configuration/self-test error) → job fails loudly, indicates a tooling problem rather than a code problem.
